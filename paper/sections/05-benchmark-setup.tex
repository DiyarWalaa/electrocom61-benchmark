\subsection{Models evaluated}
\label{sec:models-evaluated}

Five detectors were evaluated: YOLOv9s, YOLO11s, YOLOv12s, YOLO26s and
RT-DETR-l. The selection serves two purposes. The first three appear in the
comparison tables of both prior studies of ElectroCom61
\citep{yolov12paper,yolov13paper}, and are included so that the present
benchmark can be placed alongside theirs. The remaining two have not previously
been applied to this dataset: YOLO26s, released in January 2026, is the most
recent member of the YOLO family and removes non-maximum suppression from its
detection head; RT-DETR-l is a transformer-based detector, included to test
whether the convolutional family adopted by all prior work on this dataset is
the appropriate choice or merely the familiar one.

All YOLO variants were used at the ``s'' (small) scale, matching prior work and
reflecting the deployment constraint that motivates the application: a
conveyor-belt sorting system runs on modest hardware. RT-DETR is not available
at an equivalent scale within Ultralytics, so the smallest provided variant,
RT-DETR-l, was used. Its higher parameter count and computational cost are
reported alongside its accuracy in Section~\ref{sec:results} rather than treated
as a confound.

YOLOv13 was not evaluated, despite appearing in one prior study of this dataset
\citep{yolov13paper}. It is not among the architectures provided by the
Ultralytics release used here, so evaluating it would have required installing
software that no other run in this benchmark used, changing the framework under
which every other model was trained. Holding one release constant across all ten
runs was judged more important than covering one additional architecture. This
constraint is itself relevant to the comparability of published results on this
dataset and is returned to in Section~\ref{sec:discussion}.

\subsection{Training configuration}
\label{sec:training-configuration}

Apart from the architecture under test, all ten runs used an identical
configuration, with one exception described in Section~\ref{sec:rtdetr-lr}.
Table~\ref{tab:training-config} lists every setting that prior work states or
that this study decided, together with its provenance.

Seven settings were copied directly from prior work: 100 epochs, batch size 16,
the AdamW optimiser, an initial learning rate of 0.01, weight decay 0.0005, and
a Tesla P100 GPU, together with the three replicated architectures. Both prior
studies of this dataset state these values \citep{yolov12paper,yolov13paper}.
The choice to copy them is deliberate. If the results reported here differ from
published ones, the training configuration cannot be offered as the explanation.

Seven further settings were added because neither prior study states them.
Three concern reproducibility directly: a fixed random seed of 0, deterministic
execution, and the Ultralytics version. Two concern training behaviour: early
stopping with a patience of 15 epochs, and initialisation from COCO-pretrained
weights. The remaining two are the RT-DETR learning rate discussed in
Section~\ref{sec:rtdetr-lr} and the two architectures not previously applied to
this dataset.

Input resolution was fixed at 640 pixels. This is not a free choice: the dataset
is distributed at $640 \times 640$, having been resized during its own
preparation, so any other value would resample an already-resampled image.
Neither prior study states an input resolution as a training argument, although
both describe the dataset as distributed at $640 \times 640$.

One setting differs from prior work rather than matching it. Both studies report
PyTorch 2.0.0, whereas the present work uses 2.5.1+cu121. Neither states an
Ultralytics version, which is the more consequential omission: the Ultralytics
release determines the layer composition, detection head, loss function and
augmentation defaults of every model it provides, so two studies may both report
results for ``YOLOv9s'' while training architectures that differ.

The optimiser was specified explicitly rather than left at the Ultralytics
default of \texttt{optimizer="auto"}, which selects an optimiser and silently
overrides the initial learning rate supplied by the user. A configuration that
appears to specify a learning rate may therefore not use it.

\subsection{A configuration that is uniform but not neutral}
\label{sec:rtdetr-lr}

Under the configuration described above, RT-DETR-l did not train. Its three
training loss terms -- GIoU, classification and L1 -- took finite values through
epoch 6 and became NaN together at epoch 7, after which none returned to a finite
value, and both validation mAP@50 and mAP@50--95 were exactly zero for every
epoch from 7 to 19. The
run was unstable well before that point: the three validation loss terms were NaN
at epochs 2, 3, 5 and 6, finite only at epochs 1 and 4, although detection metrics
continued to be computed at those epochs. Early stopping halted the run at epoch
19, and the best checkpoint was therefore taken from epoch 4, the last epoch at
which the validation losses were finite and before the training terms diverged.
Re-evaluated, that checkpoint reaches 0.0039 mAP@50 and 0.0016 mAP@50--95 on
validation, and 0.0057 and 0.0026 on test.

Reducing the initial learning rate from 0.01 to 0.0001 -- a factor of one hundred
-- and changing nothing else produced a run that converged, reaching 0.938 mAP@50
and 0.6016 mAP@50--95 on validation, and 0.9171 and 0.6045 on test, with the best
checkpoint at epoch 58. Both runs are retained in the repository.

The sensitivity is not itself surprising. Transformer-based detectors are commonly
trained at learning rates one to two orders of magnitude below those used for
convolutional detectors, and the value adopted here was drawn from studies that
evaluated only YOLO variants. What matters is the methodological consequence. A
single configuration applied uniformly to every model is often taken to be the
fair basis for a comparison. Across architecture families it is not: the same
value that trains four convolutional detectors to convergence prevents a
transformer from training at all. Uniformity of configuration and fairness of
comparison are distinct properties, and the first does not imply the second.

The results reported for RT-DETR-l in Section~\ref{sec:results} therefore use
lr0 = 0.0001. This is the single respect in which the ten runs differ, and it is
recorded as such in Table~\ref{tab:training-config}.

\subsection{Evaluation protocol}
\label{sec:eval-protocol}

Each model was trained once on each split and evaluated on both the validation
and the test partition of that split, giving ten training runs and twenty
evaluations. Training used the training partition alone; the validation
partition served for early stopping and best-checkpoint selection; the test
partition was not consulted until training had completed.

Four accuracy quantities are reported. mAP@50 is included because it is the only
accuracy metric prior work on this dataset reports, and comparability requires
it. mAP@50--95, the COCO standard, averages precision over ten
intersection-over-union thresholds rather than one and is therefore sensitive to
localisation quality as well as to detection; no published study on this dataset
reports it. Precision and recall are reported for completeness, and per-class
average precision is reported for all classes, which no published study on this
dataset provides.

A fifth quantity is reported that is not a performance measure: the number of
classes on which the evaluation was actually computed. The framework reports
this directly. Under the published split it is 45 on validation and 46 on test
rather than 61, for the reasons established in Section~\ref{sec:dataset-audit}.
The two figures differ by a single class, ESP32, which carries 190 training
instances, two test instances and none in validation. Every mAP figure computed
on the published split is therefore an average over a reduced set of classes,
and reporting the count alongside the score is what makes results on the two
splits comparable at all.

The training configuration recorded an intersection-over-union threshold of 0.7
for non-maximum suppression and a maximum of 300 detections per image, identical
across all ten runs. The confidence threshold was left unset and is resolved by
the framework at run time according to evaluation mode; its value is therefore
fixed by the Ultralytics release stated in Section~\ref{sec:training-configuration}
rather than specified here. We record this as an instance of the same reporting
gap identified above: an evaluation configuration can be documented in full and
still contain a threshold determined by a library version, which is precisely
why that version must be reported.

\subsection{Efficiency measurement}
\label{sec:efficiency-measurement}

Model complexity is reported after fusing batch normalisation into the preceding
convolution, since that is the form in which a model is deployed. Both figures
were measured. Fusion reduces YOLO26s from 9{,}995{,}078 parameters and 22.998
GFLOPs to 9{,}488{,}787 and 20.892, and RT-DETR-l from 32{,}931{,}431 and
110.159 to 32{,}109{,}095 and 105.6. The reduction ranges from 0.2\% to 5.1\% of
parameters depending on architecture. Of the published studies reporting results
on this dataset, the two that report parameter counts
\citep{yolov12paper,yolov13paper} do not state whether those counts are fused or
unfused, and the dataset paper \citep{electrocom61} reports none at all: its
results table carries only mAP@50, precision, recall, F1 and total loss. The
difference is large enough to matter when parameter counts are compared across
papers.

Latency was measured at batch size one, at 640 pixels, on the same Tesla P100
used for training. Batch size one is the quantity of interest: it is the time to
process a single image, which is what a conveyor-belt application experiences.
Larger batches measure throughput, a different property.

Four precautions were taken. Twenty inferences were run and discarded before
each model was timed, because the first inferences after a model is loaded are
several times slower while CUDA kernels compile and the device raises its clock.
A further thirty images were run on one model before the loop began and
discarded, absorbing one-time initialisation costs that would otherwise have
fallen entirely on whichever model happened to be measured first.
\texttt{torch.cuda.synchronize()} was called before stopping the clock on each
image, because GPU execution is asynchronous and timing without it measures how
quickly Python enqueues work rather than how quickly the device completes it.
The median and 95th percentile are reported rather than the mean, because a
single outlier distorts a mean and because, for a conveyor application, the
near-worst case is more informative than the average.

All ten checkpoints were measured consecutively within a single session. This was
necessary rather than convenient: an earlier set of measurements taken across ten
separate sessions differed by 5.65~ms for the same architecture (18.58 against
24.23~ms for YOLOv9s), or 26\% of their mean. A further precaution was
established by an intermediate pass over the same ten checkpoints, identical to
the released one except that the image files were not read before timing. In that
pass the first model measured returned an end-to-end median of 51.29~ms against
47.00~ms for the identical model measured later in the same pass, a difference of
4.29~ms or 8.7\% of their mean, while their inference times differed by 0.18~ms,
or 0.43\%. The discrepancy therefore lay outside the measured stages, and was
traced to the first read of each image file from network-mounted storage. Reading
all 205 images once before timing eliminated it: in the released pass the same two
runs differ by 0.12~ms, or 0.25\%. Both passes are retained in the repository.

Because latency is a property of the architecture rather than of the split a
model was trained on, the two runs of each architecture constitute duplicate
measurements. Across five architectures the largest difference between a pair was
0.24~ms, or 1.75\% of their mean. This is reported as the resolution of the
measurement, and differences of that order between models are not treated as
meaningful. Every spread quoted in this subsection is expressed as a percentage
of the mean of the two measurements it describes.

Two distinct timing quantities are reported. The framework's own
preprocess, inference and postprocess breakdown measures the stages it controls;
the end-to-end duration of the \texttt{predict()} call is larger, the difference
being framework overhead such as result-object construction and format
conversion. Reporting only the former would make a model appear faster than an
application using it would observe.

\subsection{Reproducibility artifacts}
\label{sec:artifacts}

Every figure and table in this paper is produced by a script in the accompanying
repository from a data file in the same repository; no value in either is
transcribed by hand into the paper. Each generating run writes a directory
recording its inputs, their
content hashes and the values derived from them, so that any reported figure can
be traced to the measurement that produced it. Figures are associated with their
generating run by script hash rather than by timestamp, because repeated renders
can produce several directories within seconds of one another. The one exception
is the provenance column of Table~\ref{tab:training-config}, which records
whether each setting was stated by prior work and is therefore a reading of those
papers rather than a measurement; it is stored as a data file and carries the
citation supporting each entry.

The corrected split is released as a manifest assigning each image to a
partition, under the same licence as the source dataset. Applied to a copy of
ElectroCom61 v2 it reproduces the split exactly: the seed is fixed and the
allocation deterministic. No image is modified, added or removed.

The ten trained checkpoints are retained in the notebook outputs from which they
were produced, and the repository carries each run's configuration snapshot,
training curves and per-class average precision. The run that failed to converge
is retained alongside them and marked as such, since a configuration reported as
unusable should be inspectable. Library versions are stated in
Section~\ref{sec:training-configuration} rather than in a supplementary file,
because as established there the framework release determines the model
definitions and is therefore part of the specification of what was trained.
