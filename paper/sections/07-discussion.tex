The benchmark in Sections~\ref{sec:benchmark-setup} and~\ref{sec:results} was
built to settle a disagreement in the published record. What it establishes is
narrower and more useful than a winner: that the disagreement was never about
the models.

\subsection{Why published results on this dataset disagree}
\label{sec:disagreement}

At least four properties differ between the published comparisons on
ElectroCom61, and none of the comparisons states which value it used for any of
them. Each is enough on its own to move a reported figure by more than the
differences the comparisons are drawing conclusions from.

The first is the version of the dataset. The archived notebook that produces the
dataset paper's headline figure downloads Roboflow export version 5, while the
archive published at the Mendeley DOI is version 9 \citep{electrocom61}; the two
differ in image count and in the preprocessing applied before export, as
Section~\ref{sec:metadata-provenance} documents for the metadata that travels
with them. Neither benchmark study states which version it used
\citep{yolov12paper,yolov13paper}.

The second is the evaluation partition. In the archived notebook the evaluation
command is run without a test-split argument, so the reported figure is a
validation-set score; the test directory is never passed to an evaluation
command anywhere in it. Neither benchmark study states which partition its
figures come from. A validation score and a test score are different quantities
even when the split is sound, and the notebook selects its best checkpoint on
the same partition it then reports.

The third is how many classes the figure averages over. Under the published
split any mAP averages 45 classes on validation and 46 on test rather than 61,
for the reasons established in Section~\ref{sec:class-coverage}. A figure
produced under a protocol that reaches all 61 classes is not the same quantity
as one produced under a protocol that reaches 46, and the fifteen classes that
differ between them are not a random sample --- they are among the most heavily
annotated in the dataset.

The fourth is the framework. Neither study states an Ultralytics version
\citep{ultralytics}, which is what fixes the layer composition, detection head,
loss function and default augmentation of every model distributed under a given
name, so two studies can report results for the same architecture while training
different networks.

The complexity columns are separable from the accuracy ones, because both
studies do state parameter counts, and those can be set beside measured values
directly. For the three architectures common to their tables and to this study,
the published counts are 0.26, 2.13 and 8.46 times the values measured here:
2.5~M against 9.44~M for YOLO11s, 19.7~M against 9.25~M for YOLOv12s, and
60.8~M against 7.19~M for YOLOv9s. The discrepancies run in both directions, so
no single systematic offset accounts for them. Fusing batch normalisation into
the preceding convolution --- the one convention difference these papers leave
unstated, and the obvious candidate --- moves a parameter count by at most 5.1\%
in this study's own measurements, and every published value here falls outside
the interval between the fused and unfused figures. Fusion therefore explains
none of them.

The two papers report the same seven rows with identical values, and the second
adds one row for its own architecture. Whatever the source of those seven
figures, they were not independently re-derived by the second study, so the
published record contains one measurement of them rather than two agreeing
ones. That bears on how much evidence stands behind the numbers, and it is
stated here as a property of the record. What produced the discrepancy is not
established: a different variant, input resolution, class count or framework
release would each be sufficient, and none of the papers states which of those
it held fixed.

None of this establishes that any published figure is wrong. Each of the four is
a property that a reader needs in order to know what a number refers to, and
that the published record does not supply. The claim is that the figures are not
comparable with one another --- which is a question about reporting, and is
answerable by reporting.

\subsection{What would have caught it}
\label{sec:what-would-have-caught-it}

The coverage defect was invisible at the level at which splits are normally
checked. Aggregated over all 2121 images the published split reads 69.7 / 20.7 /
9.7, which is a textbook 70/20/10, and it reaches that figure through deviations
that cancel (Section~\ref{sec:allocation-uniformity}). A reader verifying the
split ratio would have found nothing.

Three checks would have found it, none of which requires training a model and
each of which costs minutes. Count the classes with no instances in the
evaluation partitions. Compute the allocation of each capture session
separately, rather than the aggregate. Read the number of classes the evaluation
framework actually scored.

The third is the cheapest and the most telling, because it requires no extra
work at all. Ultralytics reports that count on every evaluation it runs. It was
printed on every evaluation any of these studies performed, and it read 45 or 46
against a dataset described throughout as having 61 classes. Reporting it beside
the score --- as Section~\ref{sec:eval-protocol} does here --- would have made
the defect self-evident without anyone looking for it.

\subsection{What generalises beyond this dataset}
\label{sec:generalisation}

Nothing about the defect is specific to electronic components. It arises
whenever data is collected in sessions and split by image: any class
photographed only within sessions that happen to fall entirely in training
becomes unevaluable, and a randomly drawn image-level split does not prevent
this, because randomness over images is not randomness over sessions. Medical
images grouped by patient, agricultural images by field, industrial images by
production run all have the same structure.

The audit that found it needed no pixels and no model. Filenames, label files
and the metadata shipped with the archive were sufficient to establish the
coverage gap, its mechanism and its extent. That matters for whether such a
check is worth running: it is not a research contribution, it is a few minutes
of arithmetic over files that any user of a dataset already has.

The transferable lesson is the direction of the error. A split defect is assumed
to inflate scores, because the familiar defect is leakage --- a test image also
seen in training is easy for the wrong reason. Here the defect was exclusion
rather than leakage, and what it excluded was disproportionately easy, so it
\emph{deflated} the scores (Section~\ref{sec:accuracy}). ``A broken split means
inflated results'' is a useful heuristic and not a rule. A defect that
understates is the harder one to notice, because nobody audits a result for
being too low.

\subsection{Reporting speed changes the answer}
\label{sec:speed-changes-the-answer}

On accuracy alone, these five architectures are close enough that the choice
between the three occupying the middle of the field is not resolvable at a
single seed: they are separated by 0.0023 mAP@50--95 on the corrected split
(Section~\ref{sec:metric-choice}). Adding latency resolves it immediately, and
not by a small margin --- the same three span 33.53~ms, roughly 140 times the
measurement's own spread.

The complexity proxy most often reported in its place would have misled. Ordered
by parameter count, these architectures fall in an order almost unrelated to
their measured speed: the one with the fewest parameters is the second slowest
of the five (Section~\ref{sec:efficiency}). A study offering parameter counts as
a stand-in for deployment cost would have handed a reader the wrong ordering,
and nothing in such a study would reveal that.

A speed ranking is also uninterpretable without a repeatability figure beside
it. The 0.96~ms separating the two fastest architectures here means something
only because the same architecture measured twice varies by 0.24~ms
(Section~\ref{sec:efficiency-measurement}); with the first number alone a reader
cannot tell a real ordering from measurement noise, and the two smallest
differences in Table~\ref{tab:efficiency} are of the same order as the noise.

The application that motivates this dataset is a conveyor belt that does not
stop for the detector. Whether a model keeps up is the question that decides
deployment, and it is not expressible in any accuracy metric. No prior study of
this dataset measured inference speed, so none of them could answer it --- not
because their measurements were poor, but because they measured a different
thing.
