FINDINGS

1. THE CHECK WAS NOT RUN, and the reason has changed since the first version of this file.
   That version recorded the blocker as "the package is absent and CLAUDE.md forbids
   installing it without asking". Permission to read the source was subsequently granted,
   explicitly scoped to a source-read outside the repository with no install and no
   dependencies. That is exactly the right scope for the question -- reading ap_per_class
   does not require a working import -- and it was attempted. It was denied by the
   repository's own guard.

2. EVERY FETCH ROUTE IS BLOCKED BY scripts/deny_guard.py, BY DESIGN. The guard's module
   docstring states its purpose as "block destructive and network-installing commands
   outright". Its rule table denies, case-insensitively and anchored at the start of a
   command segment:
     - curl, wget, invoke-webrequest, invoke-restmethod, iwr, irm, start-bitstransfer,
       classified as "network download"
     - pip, pip3, conda, npm, npx, winget, choco, mpm, miktex, and python -m pip,
       classified as "package installation"
     - git clone from any remote spelling, classified as "network clone"
   Between them these cover every way of obtaining a PyPI sdist or a GitHub tag. The block
   is not incidental to this task; it is the guard working as specified.

3. NOTHING WAS DOWNLOADED AND NOTHING WAS LEFT ANYWHERE. The attempt was made as a single
   command that created a directory outside the repository and then fetched into it. The
   guard blocked the command before any part of it ran, so C:\research\ultralytics-src was
   never created; its absence was confirmed afterwards. No archive of any kind exists
   anywhere in the repository. The working tree carried no untracked file as a result.

4. THE GUARD ALSO DENIES DELETION, so had a tree been created it could not have been removed
   from here. This is documented behaviour: .gitignore carries three separate notes
   recording files that "cannot be deleted from here -- scripts/deny_guard.py denies
   deletion -- so remove it by hand". Any future run of this check should assume the same,
   and should place the extracted tree where a hand cleanup is expected rather than
   promised.

5. NO ANSWER IS OFFERED, TO EITHER QUESTION. The working rule for this series is that a
   value or a behaviour is read from the source and cited by location, never stated from
   memory, and that rule binds hardest when the expected answer is one a reader would find
   plausible. The brief states the expected mechanism -- that the confusion matrix is built
   at nc+1 to account for unmatched predictions and missed ground truths while mAP is
   computed on a separate path -- and that is very likely correct. This report cannot
   confirm it and therefore does not.

6. THE VERSION'S AVAILABILITY WAS NOT EVEN CONFIRMED. The metadata lookup and the download
   were issued as one command and the whole command was denied, so the PyPI response was
   never seen. This report cannot state that 8.4.115 is or is not published as an sdist. The
   instruction to stop rather than read a neighbouring release stands and was not reached:
   nothing was read.

7. THE SECOND QUESTION IS THE MORE LOAD-BEARING OF THE TWO and is entirely unaddressed. What
   the framework's "classes evaluated" count is counting -- classes with instances in the
   evaluation set, or classes with predictions, or a range over nc -- decides what the 45
   and 46 figures mean, and Sections 3.1, 5.4 and 6.1 all rest on those two numbers. Note
   that this does NOT put those sections in doubt: 45 and 46 are values this study read off
   its own runs and they are reproduced by scripts/verify_eval_protocol.py, which passes.
   What is unestablished is the semantics of the count, not its value.

COULD NOT DETERMINE

Both questions the check was asked to settle:
  - whether a background class can enter the mAP average in 8.4.115;
  - what the framework's printed "classes evaluated" count enumerates.

And one thing incidental to them: whether 8.4.115 is published on PyPI as a source
distribution at all.

The blocker is scripts/deny_guard.py, which denies every command that could fetch the
source. Permission from the repository owner is not sufficient on its own, because the guard
is a committed control enforced by a hook rather than a matter of policy. Resolving it needs
one of:
  - the owner fetching and extracting the 8.4.115 sdist by hand into a directory outside the
    repository, after which this check is a pure read and needs no network at all;
  - or a deliberate, owner-made change to the guard's rule table, which is a larger decision
    than this check warrants and is not recommended for it.
The first is cheap, leaves the guard intact, and is the recommended route. A hand cleanup
will be needed afterwards for the same reason: the guard denies deletion.
