FINDINGS

1. THE QUESTION IS ANSWERED, AND NOT BY THE ROUTE PLANNED. Both earlier versions of this
   file treated the answer as reachable only by reading ap_per_class in the installed
   package. It was not necessary. A released training log preserves the DetMetrics object
   the framework returned, and that object carries the per-class array the mAP is averaged
   over. The evidence is the framework's own output on a known dataset, which is stronger
   for this question than reading the code that produces it: it shows what the code did,
   not what it should do.

2. NO BACKGROUND CLASS ENTERS THE mAP AVERAGE. The dataset has 61 classes -- the log prints
   "Overriding model.yaml nc=80 with nc=61" -- and the returned maps array has EXACTLY 61
   entries. A background term would make it 62. It does not.

3. THE ARRAY WAS CHECKED FOR ELISION BEFORE THE LENGTH WAS TRUSTED. The DetMetrics repr
   contains 28 occurrences of "...", numpy eliding its long curves_results arrays. Neither
   the maps text nor the nt_per_class text contains "...", and both parse to exactly 61
   values. An elided array would have made the length argument worthless.

4. THE PRINTED CLASS COUNT ENUMERATES CLASSES WITH INSTANCES IN THE EVALUATION SET. In the
   same log, nt_per_class has 61 entries of which 16 are zero and 45 are non-zero, and
   ap_class_index -- the classes for which an AP was actually computed -- has 45 entries and
   is exactly the complement of the 16 zeros. So the count is over classes carrying at least
   one instance in the partition being evaluated, not a range over nc and not a count of
   classes with predictions.

5. THE DENOMINATOR OF THE REPORTED mAP IS THE NON-ZERO SET. The reported mAP50-95 is
   0.582854 and the mean of the 45 non-zero entries is 0.582854. The 16 zero-instance
   entries each carry 0.58285, the overall mean used as a placeholder, so a mean over all 61
   returns 0.582853 -- the same number to five decimals, by construction. That agreement is
   not independent evidence of anything and is recorded here only so the placeholder
   convention is on the record. THE LENGTH IS WHAT RULES OUT A BACKGROUND TERM.

6. WHAT THIS MEANS FOR C09. That report's closing paragraph gives two reasons why a
   published mAP and one computed here may not share a denominator: that none of the three
   papers states the class count its mAP was averaged over, and that all three publish
   confusion matrices carrying a background row and column. THE FIRST REASON STANDS
   UNCHANGED and is established by direct reading of the three papers. THE SECOND SHOULD BE
   STRUCK: the confusion matrix is built at nc+1 and the mAP is not, so the presence of a
   background row in a published figure says nothing about the mAP's denominator. C09's
   conclusion does not change; one of its two supports does.

COULD NOT DETERMINE

WHETHER 8.4.115 BEHAVES AS 8.3.160 DOES. This log is Ultralytics 8.3.160; this study ran
8.4.115. Nothing here establishes that the metric plumbing is identical across those
releases, and Section 7.1 argues at length that a framework release fixes model definitions
and should not be assumed stable. For the denominator question the risk is low -- a
background term entering the mAP average would be a substantial behavioural change, not a
version drift -- but it is an assumption and is named as one.

IF THAT ASSUMPTION EVER NEEDS CLOSING, the source read is still the way, and the plan from
the earlier version of this file stands: ultralytics/utils/metrics.py, function
ap_per_class, for what array it iterates over; the DetMetrics aggregation in the same file,
for how the per-class vector is reduced; and class ConfusionMatrix, for where the nc+1
dimension is introduced. THE SDIST FETCH IS NO LONGER NEEDED FOR THE DENOMINATOR QUESTION
and would be needed only to settle the cross-version point above.

IMPACT ON THE MANUSCRIPT

None, and none is intended. No sentence depends on the question, and this report does not
create one. Sections 3.1, 5.4 and 6.1 rest on the 45 and 46 evaluated-class counts, which
are measured from this study's own runs and reproduced by scripts/verify_eval_protocol.py;
this check adds the semantics of that count and confirms it is what those sections assume --
classes with instances in the partition evaluated.

One downstream edit is now due in the reports rather than the paper: strike the
confusion-matrix half of C09's closing inference and leave the half resting on the three
papers' silence about their class counts. That half is established and is the one the
manuscript would ever rely on.
