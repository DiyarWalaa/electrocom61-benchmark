IMPACT ON THE MANUSCRIPT

Nothing in the manuscript was changed on the strength of this check; the brief said report
first. Two questions were asked specifically.

SECTION 5.2's CLAIM DOES NOT SURVIVE UNQUALIFIED, AND SHOULD BE NARROWED. It reads: "If the
results reported here differ from published ones, the training configuration cannot be
offered as the explanation." That rests on this study having copied seven settings from the
prior papers, one of which is lr0=0.01. The released code passes no learning rate at all,
leaves optimizer=auto, and Ultralytics then explicitly ignores lr0=0.01 and trains AdamW at
0.000154. This study sets lr0=0.01 and means it. So for at least this one prior study, the
learning rate actually used differs from this study's by a factor of 65, and the training
configurations are not the same in the respect the sentence needs them to be. The claim is
still true of the values the PAPERS STATE -- both state lr0 0.01 and AdamW, and this study
reproduces both -- but the released code shows the stated value was not the operative one.
The honest repair is to scope the sentence to the stated configuration and note what the
released code shows, which is a stronger point than the one the sentence currently makes:
it is a concrete instance of the reporting gap Section 7.1 argues for.

SECTION 6.3's "FOR THE SAME ARCHITECTURE" IS NOT SAFE AS IT STANDS. The sentence sets this
study's YOLOv12s measurement beside the published 89.1% "for the same architecture". The
published row is labelled YOLOv12S at 19.7 M parameters; the released code loads
yolov12n.pt and prints 2.5 M. Those are different architectures, and the difference is a
factor of 7.8 in parameters, not a fusion or counting convention. Three readings are
available and the file does not choose between them: the table's label is right and the
notebook is a different run; the notebook is the run behind the table and the label is
wrong; or neither. What can be said without choosing is narrower and still useful -- that
the released training code loads the nano checkpoint while the table reports the small
variant, which is exactly the kind of unstated condition Section 7.1 lists. Section 6.3
should either drop "for the same architecture" or carry the qualification.

ON SECTION 7.1, this check strengthens two of the four properties rather than changing them.
The evaluation partition is now settled for this study rather than merely unstated: the
released code evaluates on validation and never on test. The framework release is settled
too: 8.3.160. Both were listed as unstated in the PAPER, which remains true; the notebook is
a separate object and 7.1 should keep saying what the paper does and does not state.

ON C14. N7 answers that report's first question -- whether a background class can enter the
mAP average -- from a released log of the framework in operation: the maps array is 61 long
for a 61-class dataset, so no background term is present. C14 is updated accordingly and no
longer needs the 8.4.115 sdist for the denominator question. Its second question, what the
printed "classes evaluated" count enumerates, is also answered here in substance: 45 is the
count of classes with a non-zero nt_per_class, i.e. classes with instances in the evaluation
set. Note the version difference -- this log is 8.3.160 and this study ran 8.4.115 -- so the
source read remains the way to establish the behaviour for the exact release this study
used, if that is ever needed.
